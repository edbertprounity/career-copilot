**Design as built**: Detection is unchanged and runs first. The template text is the draft Gemini rewrites, so every fact an issue rests on is in what Gemini sees. The payload per issue is issue_id, type, severity, section, quote, context (its CV section; empty for "Job ad") and the draft. The student's full name and each part of it are replaced with `[name]`. Issues in the name line (`Summary`) and `Contact` are never sent; they keep template text with reason `private_section`. The response schema asks for issue_id, quote, why, suggestion and question per issue, and anything else returned (type, severity, section) is ignored. A returned field is used only if all of these hold: the echoed quote equals the quote sent (whitespace-normalised), so text cannot drift to another issue; each field is a non-empty string of at most 300 characters; no field matches `_BANNED_WORDING_RE` (lack, don't have, not qualified, unqualified, hire/hired/hiring, employer will, shortlist, reject, your chances, not a fit); and every claim `ungrounded_terms` finds is supported by `profile_supports` or already appears in the issue's own quote, draft or section name. Any failure keeps that issue's template. Diagnostics: `{"path": "gemini" | "partial" | "template", "reason", "detail", "issues": {issue_id: {"source", "reason", "detail"}}}`, with batch reasons `disabled`, `no_issues`, `private_section`, `no_client`, `api`, `parse` and `empty`, and per-issue reasons `missing`, `quote_mismatch`, `empty_field`, `too_long`, `banned` and `ungrounded`.
